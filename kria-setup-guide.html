Complete Setup Guide: Kria KR260 and KV260

This guide documents the essential steps for configuring an AMD/Xilinx Kria KR260 or KV260 from a fresh installation to a development-ready environment. The resulting system can be configured for JupyterLab, Remote SSH development, FPGA development, embedded applications, and audio DSP experimentation.

Note: This guide documents the development environment and configuration procedures used for this project. It is not intended to replace the official AMD/Xilinx documentation. Software versions, package availability, supported applications, and installation procedures may change over time between platforms and software releases.
Platform Note: The KR260 and KV260 use the Kria K26 SOM platform, allowing many Ubuntu and network-level configuration procedures in this guide to be applied to both boards. However, platform-specific applications, hardware interfaces, and PYNQ installation options should always be verified for the target board.

1. System Optimization: Reducing SD Card Wear

By default, Ubuntu continuously writes system logs to persistent storage. On systems running from an SD card, reducing unnecessary write activity can help minimize storage wear.

This configuration changes systemd-journald storage to volatile memory.

Configure Journald

Open the Journald configuration file: 

sudo nano /etc/systemd/journald.conf

Locate the following line: 

#Storage=auto

Remove the comment marker and change it to: 

Storage=volatile

Save the file using Ctrl+O, press Enter, and exit with Ctrl+X.

Restart the Journald service: 

sudo systemctl restart systemd-journald
Note: With Storage=volatile, system logs are stored in RAM and will be lost after a reboot.

2. Practical Network Setup with mDNS

Using mDNS allows a Kria board to be accessed through a hostname instead of requiring its dynamically assigned IP address.

The following configuration can generally be applied to both the KR260 and KV260.

Install Avahi

Update the package list and install the required packages: 

sudo apt update
```

sudo apt install avahi-daemon libnss-mdns -y
```

Configure the Hostname

You can assign a hostname according to the target platform.

KR260 
sudo hostnamectl set-hostname kria-kr260
KV260 
sudo hostnamectl set-hostname kria-kv260

Alternatively, a shared hostname such as kria may be used if only one Kria board is present on the local network.

Enable the Avahi Service

Enable and restart the service: 

sudo systemctl enable avahi-daemon
```

sudo systemctl restart avahi-daemon
```

The board can then be accessed through its configured hostname.

KR260 
kria-kr260.local
KV260 
kria-kv260.local

Example SSH connections: 

ssh <USERNAME>@kria-kr260.local

or: 

ssh <USERNAME>@kria-kv260.local

3. Board Access and Basic Environment Commands

This section provides several commonly used commands for accessing and managing the Kria development environment. Some commands may require platform-specific configuration depending on the operating system image and host computer.

Serial Console Access

A serial connection can be used for initial board configuration, troubleshooting, or accessing the system when network connectivity is unavailable.

From Windows PowerShell, PuTTY's command-line utility can be used as follows: 

plink -serial <COM_PORT> -sercfg 115200,8,n,1,N

Replace <COM_PORT> with the serial port assigned to the Kria board by the host operating system.

SSH Access

After network connectivity and mDNS have been configured, the board can be accessed through SSH.

KR260 
ssh <USERNAME>@kria-kr260.local
KV260 
ssh <USERNAME>@kria-kv260.local

Replace <USERNAME> with the appropriate user account configured on the target system.

Checking the Network Configuration

The current network interface configuration can be inspected using: 

ifconfig

On newer Linux distributions, the following command may also be preferred: 

ip addr

Entering a Root Shell

Administrative commands can be executed through a root shell when required: 

sudo -E su
Security Note: Use a root shell only when necessary. Commands executed as the root user can modify or remove critical system files without the usual permission restrictions.

Activating the PYNQ Virtual Environment

Depending on the installed PYNQ version and system configuration, the PYNQ environment may need to be activated manually before running Python-based PYNQ applications. 

source <PYNQ_VENV_PATH>/bin/activate

For example, the environment path may be located under a shared system directory such as: 

source /usr/local/share/pynq-venv/bin/activate
Note: Verify the installed virtual environment location on the target system, as the path may differ depending on the PYNQ version and installation method.

4. Installing PYNQ and Handling Unattended Upgrades

Ubuntu may automatically run background package updates shortly after the board obtains an internet connection.

During this process, the package management system may be locked by another process. This can interfere with the PYNQ installation process and potentially cause installation failures or timeouts.

Disable Unattended Upgrades

Stop the currently running service: 

sudo systemctl stop unattended-upgrades

Disable automatic updates through the package configuration interface: 

sudo dpkg-reconfigure -plow unattended-upgrades

When prompted by the configuration interface, select: 

No

Reboot the board to ensure that any existing package management locks are cleared: 

sudo reboot

Install Kria PYNQ

After the board has restarted, clone the Kria PYNQ repository: 

git clone https://github.com/Xilinx/Kria-PYNQ.git

Enter the repository directory: 

cd Kria-PYNQ/

Run the installation script according to the target board.

KR260 
sudo bash install.sh -b KR260
KV260 
sudo bash install.sh -b KV260
Important: Verify the currently supported board identifiers and installation options in the Kria-PYNQ repository before running the installation script, as these may change between software versions.

Wait until the installation process is complete.

Once configured, JupyterLab can be accessed through a web browser using the hostname configured for the target board.

KR260 
http://kria-kr260.local:9090
KV260 
http://kria-kv260.local:9090

Default credentials may depend on the installed operating system image and PYNQ version. Refer to the corresponding installation documentation if the default credentials differ from the environment described in this guide.

5. Configuring a USB Sound Card as the Default ALSA Device

When using a USB sound card for audio processing, it can be configured as the default ALSA device instead of the board's default audio interface.

This procedure is applicable to both the KR260 and KV260 when the required USB audio device is supported by the Linux kernel.

Identify Available Audio Devices

List the available playback hardware: 

aplay -l

Identify the card number corresponding to the USB sound card.

For example: 

card 1: USB [USB Audio Device], device 0: USB Audio

In this example, the USB sound card uses card number 1.

Create the ALSA Configuration

Open the global ALSA configuration file: 

sudo nano /etc/asound.conf

Add the following configuration: 

defaults.pcm.card 1
```

defaults.ctl.card 1
```

Replace 1 with the appropriate card number if your USB sound card uses a different identifier.

Save the file and exit the editor.

Testing Audio Playback

After configuring the desired ALSA output device, an audio file can be played directly from the command line for testing purposes: 

aplay "<PATH_TO_AUDIO_FILE>/<AUDIO_FILE>.wav"

Replace the placeholders with the actual location and filename of a WAV file available on the board.

Adjusting Audio Volume

The ALSA mixer interface can be opened using: 

alsamixer

Select the appropriate audio device if multiple sound interfaces are available.

Note: Audio device numbering may change depending on connected hardware and driver initialization order. Verify the device number with aplay -l if the configuration stops working.

6. System and PYNQ Environment Maintenance

During development, temporary files, Python bytecode, package caches, and PYNQ-generated data may accumulate on the system. Periodic cleanup can help recover storage space and remove stale cached files during troubleshooting.

Cleaning APT and Python Package Caches

The following commands remove unused packages and cached package files: 

sudo apt autoremove
```

sudo apt clean
pip cache purge
```

Cleaning PYNQ and Python Cache Files

Additional development-related cache files can be removed using the following commands: 

rm -rf ~/.pynq
```

rm -rf ~/.cache/pynq
rm -rf ~/overlays/**pycache**

find . -type d -name "**pycache**" -exec rm -rf {} +
find . -type f -name "*.pyc" -delete

rm -rf ~/.cache/pip
```

Removing PYNQ Runtime Cache Files

Some PYNQ installations may generate cached runtime files inside the Python environment. If troubleshooting requires clearing these files, verify the PYNQ installation path before proceeding. 

sudo find <PYNQ_INSTALL_PATH>/pl_server/ \
-type f -name "*.pkl" -delete
```

sudo find /pl_server/ 
-type f -name "*.json" -delete
```

For example, a system-wide installation may use a path similar to: 

/usr/local/share/pynq-venv/lib/python<PYTHON_VERSION>/site-packages/pynq/pl_server/
Important: Verify all paths before running recursive removal commands or commands with sudo. Incorrect paths may remove files required by the operating system or development environment.

Clearing the Terminal 

clear

7. Setting Up Remote SSH in Visual Studio Code

Remote SSH allows software, scripts, and hardware-related files to be edited directly from a host computer while the development environment remains on the Kria board.

Install the Required Extension

Install the Remote - SSH extension in Visual Studio Code.

Configure the SSH Connection

Open the SSH configuration file.

On Linux: 

~/.ssh/config

On Windows: 

C:\Users\<Username>\.ssh\config

You can create separate SSH configurations for each platform.

KR260 
Host kria-kr260
HostName kria-kr260.local
User <USERNAME>
KV260 
Host kria-kv260
HostName kria-kv260.local
User <USERNAME>

Save the configuration file.

Connect to the Kria Board

Open the Visual Studio Code Command Palette and select: 

Remote-SSH: Connect to Host

Then select the appropriate target: 

kria-kr260

or: 

kria-kv260

When prompted, enter the password for the configured user account.

After the connection is established, Visual Studio Code can be used to edit and manage files directly on the target Kria platform.

8. Shutting Down the Board Safely

Before disconnecting power from the Kria board, shut down the operating system properly to reduce the risk of filesystem corruption. 

sudo shutdown -h now

Wait until the operating system has completed the shutdown process before disconnecting the power supply.

Note: This command shuts down the complete operating system. It does not simply disable the programmable logic or FPGA fabric.

Development Environment Summary

After completing the configuration described in this guide, the Kria KR260 or KV260 can provide the following development environment:

  • Reduced persistent system log writes to the SD card.
  • Network access through an mDNS hostname.
  • Serial and SSH access for board management and development.
  • PYNQ and JupyterLab support for interactive development.
  • Remote development through Visual Studio Code and SSH.
  • USB audio device configuration for audio DSP experimentation.
  • Basic maintenance procedures for package, Python, and PYNQ-related cache files.
  • A practical environment for FPGA development, hardware accelerators, embedded systems, and DSP projects.

Although many software-level configurations are shared between the KR260 and KV260, hardware-specific interfaces, applications, and supported development workflows may differ between the two platforms.
